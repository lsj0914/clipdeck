# Media preparation and rendering

ClipDeck reads original video files in main. The renderer receives random, revocable `clipdeck-media://media/<id>` addresses for verified MP4 files. Native source paths are never returned by the bridge. Requests are restricted to the owning desktop window's media element; the protocol rejects unknown IDs, alternate authorities, query/path injection and malformed/multiple ranges. It supports GET, HEAD, normal/suffix byte ranges and seeking.

## Source audition

After import or verified native relink, main can publish an approved original MP4 as a playback candidate without encoding a source proxy. Approval comes from the native probe bound to the two import SHA-256 scans, registry generation and filesystem signature; filenames and renderer metadata cannot grant it. Candidates must have one video stream, zero container/video/audio origins, matching stream durations within one frame, zero rotation, square or absent SAR, positive frame rate up to 120 fps, dimensions up to 8192 pixels and duration at most six hours. The narrow codec policy is H.264 `avc1` with 8-bit 4:2:0 Baseline/Main/High profiles or HEVC `hvc1` Main/Main10 with 4:2:0 pixels. Main10 additionally requires an explicit BT.709 color matrix; reported HDR/BT.2020 color fields are excluded. Optional audio must be AAC-LC `mp4a`, mono/stereo at 44.1 or 48 kHz. MOV/ProRes, PCM, delayed audio, positive origins, rotation and non-square pixels use normalization.

A candidate is not proof of browser support. The workbench must establish nonzero video dimensions, an actual decoded frame and successful seeking for the current URL before treating it as ready. Metadata or `play()` alone is insufficient: ProRes, for example, can silently play only audio in Chromium. Browser failure must request `prepareSourcePreview(assetId)`, which always means a normalized H.264/AAC source proxy. This distinct cancellable `sourcePreview` job immediately retires the direct candidate for that project/source identity, even if preparation fails or is cancelled. Explicit retry remains possible. It coalesces with an existing normalized preparation and never returns a failed direct attempt as a completed proxy.

Original capabilities live outside the owned proxy cache. Cache eviction and cleanup can revoke capabilities but never remove an original file. Relinking, source changes and project switches invalidate direct authority. Approval is not persisted in project files; reopening requires native verification again. Import still hashes the entire original twice, so direct approval removes the subsequent full-source encode/validation wait, not import verification time. Native approval and protocol tests do not establish a speedup or browser codec support on every machine.

Source proxies preserve the shared source time axis and genuine delayed audio. Rotation and pixel aspect ratio are applied during normalization once. The proxy has square pixels, at most 1280 pixels on its longest display dimension, 30 fps and stereo 48 kHz audio. Duration is quantized upward by less than one frame. Original files remain the source for final assembly rendering, identity checks and transcription.

## Assembly and output

An assembly is an immutable project/revision snapshot with exact integer-millisecond source intervals. Each interval produces `ceil(durationMs * 30 / 1000)` frames and exactly 1600 audio samples per frame. Accurate input seeking bounds decoding; the filters retain only the selected interval. An interval without a selected video frame fails with an instruction to widen its bounds. Padding clones only the last selected frame and adds silence. Video/audio use the same source origin; delayed audio is not moved earlier by independent stream-origin resets.

Cuts normalize to lossless FFV1/PCM Matroska intermediates. Their integer frame/sample clocks are reconstructed for concatenation before one H.264/AAC encode. Preview uses half the output dimensions and the same source intervals, frame/sample counts, geometry and processing rules. Final output uses the selected 1920×1080, 1080×1920 or 1080×1080 preset.

Before publication, native validation fully decodes the output; checks codecs, dimensions, SAR, frame count, audio presentation samples and duration; streams every decoded video presentation timestamp against the 30 fps clock; and decodes a WAV to verify its actual sample count. Source fingerprints are fully hashed before and after processing; file and authority identities are also checked at those boundaries. A final synchronous target/source check and same-filesystem rename form the job's commit boundary. Cancellation before that boundary preserves the previous target; cancellation afterward cannot reclassify an already published result. Existing output replacement requires the native save dialog. Source aliases, including hard links and symbolic links, are rejected.

## Resource policies

- An approved original candidate, normalized source preview or assembled output is limited to six hours. Longer input sources can still be imported and edited; full-source preparation fails explicitly. Shorter selections from a longer source may be exported when the assembled duration fits the limit.
- Source preview output is capped at 4 GiB while encoding. The transient cache is capped at eight artifacts and 4 GiB total. Before publication, older inactive artifacts are revoked and removed; the most recently served player URL is protected. Evicted sources lose their snapshot URL and can prepare again. Retiring an older result removes a cache lookup only when that result still owns it, preserving a newer replacement attempt with the same key. If the protected current video and a new proxy cannot fit together, preparation fails explicitly. This is a one-player workbench cache policy, not multi-player pin tracking.
- Assembly staging is capped at 16 GiB, checked using actual file sizes during FFmpeg progress. Processing checks free space for the decoded verification audio plus 256 MiB before starting. Native disk errors fail the job and clean its own staging directory.
- The job manager runs at most two heavy jobs, including at most one transcription. Media jobs on the same filesystem share reservations for decoded audio and its free-space margin. These estimates do not guarantee compressed video size or protect against other applications consuming disk space. Cancellation reaches encoding, decode/probe validation, identity hashing and the precommit boundary. Progress comes from native processed timestamps and explicit validation stages.
- Source cache keys include content fingerprint, native source-authority generation, filesystem identity and processing rules. Playback GET, HEAD and range requests check the captured source registry generation/path plus device, inode, size, modification time and change time; they do not reread entire originals. Both served originals and proxies must match their captured identity by path and by the opened file descriptor. These checks rely on the local filesystem metadata and are not fresh cryptographic scans of original bytes on every seek. Full SHA-256 verification remains mandatory before and after media processing. Relinking, changed files, deleted proxies and a new application session invalidate old authority. Source preview jobs do not use assembly revision provenance. Assembly caches include project identity, revision, plan and sources.
- Temporary intermediates live in a unique directory beside the target. Cleanup removes only that job's directory. The application-owned transient media cache is cleared on startup; exported user files are retained.

These limits describe implementation policy, not measured support for every six-hour source, codec profile or machine. Large lossless intermediates can hit the staging/free-space limits sooner.

## Reproduction

Prepare the project-local runtimes first as documented in the worker/runtime setup. Tests and scripts consume `.runtime/bin/ffmpeg`, `.runtime/bin/ffprobe` and the bundled project-local worker; they do not discover media tools on PATH.

Run `npm test -- tests/services/source-preview-direct.test.ts tests/services/media.test.ts tests/services/render.test.ts tests/services/media-protocol.test.ts` for direct candidate authority, native processing and failure/publication tests. The direct suite generates its own H.264, origin, rotation and SAR fixtures with the product runtime. Set `CLIPDECK_DIRECT_FIXTURES` to an external directory containing `hevc-main10-sdr.mp4`, `hevc-main10-pq.mp4` and `prores-pcm.mov` to also exercise real Main10/ProRes policy and normalization; retain fixture producer commands, hashes and native probe metadata with those external acceptance inputs. That optional codec case does not claim browser decoding.

Run `node scripts/benchmark-render.mjs --output-dir=/absolute/path/outside-the-repository --runs=3` for original generated numbered/color/tone markers. It creates 60 distinct sources, mixed 24/25/30 fps, geometry, rotation, SAR and a silent source; exports them in reverse order; checks visual first/middle/last frames for every cut, audio tone order, exact counts and timing; and saves provenance/truth plus three run receipts. Output folders must be new: prior exports are not silently replaced. Timing conditions identify filesystem warming from fixture generation. Memory is sampled for Node and its native descendants every 100 ms, not a kernel high-water measurement.

After a desktop build, `scripts/smoke-media.cjs` can be launched with Electron using `--fixture-root=<explicit codec-fixture-directory> --receipt=<JSON destination> --user-data-dir=<fresh isolated profile>`. It uses the actual native workspace and guarded product protocol, requires decoded video frames and a real 2.1-second seek, and checks that a foreign window cannot play an otherwise approved URL. Its fixtures are external acceptance inputs; no demos or preset media ship in the application. This harness does not claim manual word-selection, loop-audition or installation acceptance.
